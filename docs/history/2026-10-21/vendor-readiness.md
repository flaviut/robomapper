# Vendor schedules and update readiness

> Historical record, retained as written. Later findings supersede some conclusions. Do not reuse its PIDs, staging paths or launch commands. See the [history index](../README.md) and [demonstrated backup procedure](../../guides/stopped-backup.md).

At **October 21, 2026, 04:49:59 UTC**, the robot reported **idle, 96% battery, no error and no cleaning, returning or locating activity**. The vendor updater answered **`idle`**. The saved vendor timers contain **zero enabled cleaning schedules and no next cleaning time**; their two enabled records are do-not-disturb guards, not cleaning commands. These observations close the saved-schedule and vendor-update questions left by the [earlier snapshot](readiness.md), without stopping or moving the robot.

The robot was **not reporting docked or charging**. Applying the exact deployed Valetudo status interpretation gives **discharging**, as before; this is not an independent charger measurement. At a reported 96%, charging is not inherently required for a short stopped interval, so lack of docking is not itself a reason to move the robot or a prerequisite for that interval. This does not promise a particular battery runtime, establish physical stillness, or authorize a service stop. The separate heartbeat, recovery and command-gating requirements still apply.

## What the fresh status and update replies establish

Only the relevant response fields were retained: `state=2`, `battery=96`, `error_code=0`, `in_cleaning=0`, `in_returning=0`, `is_locating=0`, `in_fresh_state=1` and `dock_error_status=0`. There was no reported cleaning, return-to-dock or locating activity. These flags and the idle state are telemetry, not an independent measurement that the chassis was physically still.

The meaning of state `2` and the battery interpretation come from `backend/lib/robots/roborock/RoborockValetudoRobot.js` at deployed Valetudo commit **`4a56bfe876c1f9b298fc5a1b3c8b213ad749ffa1`**, release **2026.05.0**. Its `STATUS_MAP` maps `2` to idle; `parseAndUpdateState()` assigns discharging when the returned state is not docked. The earlier Valetudo updater observation was `ValetudoUpdaterIdleState`, `busy=false`; that was not re-polled or substituted for vendor OTA status.

The authenticated `get_ota_state` reply was the single value **`idle`**, received at **04:49:59.411 UTC**. Unlike merely finding no `SysUpdate` process, this directly observes the vendor updater's reported state. It establishes that the vendor was not reporting a download, pending installation or installation at that instant, not that an update cannot begin later. No OTA-progress request, update operation or firmware-identification query was made.

## Why the vendor timers do not schedule a clean

The schedule file was read over SSH at **04:48:21 UTC**. It is plain ASCII in AppProxy's native cron-like format, not encrypted JSON. Both records begin with the enabled marker `Y`, have action class `2` and recurring-time class `1`, and invoke only `dnd_start` or `dnd_stop`. Their minute field is `*`; complementary hour lists cover the first and second halves of each local day. There are therefore **two enabled internal guards**, whose next matching calendar minute from the final status snapshot was **04:50 UTC**, but **no enabled vendor cleaning timer and no next scheduled clean**. The guards maintain do-not-disturb state; they are not movement commands. The separate server-timer file was empty at **04:48:06 UTC**. The earlier Valetudo timer read found zero timers, including zero enabled timers.

This interpretation comes from the matching installed AppProxy, rather than a guessed decoder. The live and saved AppProxy files matched by MD5. In `binaries/4.3.5_1612/opt/rockrobo/cleaner/bin/AppProxy`, registration at **VA `0x625e8`** maps `get_timer` to **`0x67c34`**. That handler selects action class `1` with time class `1` or `2`; neither saved record belongs to that cleaning-action class. The native parser at **`0x87614`** reads the enable marker, record name, action class, time class and five cron fields in that order. The evaluator at **`0x86d74`** recognizes enabled recurring `dnd_start` guards separately. The constructor at **`0x86930`** selects `rockrobo/apptimer.cfg` and the vendor local-time file. This was static inspection of saved firmware; original firmware code was never executed locally.

The saved-file result does not independently inspect AppProxy's in-memory timer list, and external automation remains a separate command source. Calling the registered `get_timer` would not improve that limitation without introducing a write-capable path: **`0x67c34` can remove malformed entries through `0x86b18`** after assembling its reply. No timer RPC was sent, and no schedule was disabled or rewritten.

## How the observations stayed read-only

The native OTA registration maps both `miIO.get_ota_state` and `get_ota_state` to the thunk at **`0x6e384`**, which loads the updater object and branches to **`0x35558`**. That routine reads the current updater state and serializes a reply; its state table at **`0x12088c`** contains `idle`, `downloading`, `downloaded`, `wait_install`, `installing`, `installed` and `failed`. The queried method was the proven unprefixed alias, `get_ota_state`. In contrast, the progress aliases use **`0x6e38c` → `0x33eac`**, whose nonzero-state path can invoke another updater routine after responding. That path was deliberately not used. The registered `get_status` handler at **`0x4c554`** serializes the current status fields; it does not start cleaning, move the robot or change settings.

A narrow local script reused the exact deployed Valetudo source's `MiioSocket`, codec and normal local UDP port. It performed one ordinary protocol handshake, one authenticated `get_ota_state` and then one authenticated `get_status`, without retries or method scanning. The existing local token was read privately into memory and used only for normal authentication to this robot; the script rejected any attempt to replace it from a handshake. Upstream logging was suppressed before loading the transport so that neither credentials nor generic responses entered logs or output. No credential file was created. SSH always used `BatchMode=yes`, `ConnectTimeout=10` and `StrictHostKeyChecking=yes`.

**No robot configuration, map, service or persistent process arrangement was deliberately changed.** Services stayed running. No signal, service stop, UART access, motion, docking, settings write, firmware operation, boot change or reboot occurred. Ordinary SSH/protocol handling and existing background work continued. No tests, suites, validators, replay, reviews or nested agents were run.

These are time-bound observations, not a command gate. Preserve the planned external-command hold and establish the separately required heartbeat and recovery conditions before considering a later stop. A later maintenance window must reconsider any elapsed time or changed activity, but docking is not an unresolved requirement created by this snapshot.
