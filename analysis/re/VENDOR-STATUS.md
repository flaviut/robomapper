# Vendor schedules and update readiness

The saved vendor schedule file contains **no cleaning schedules**, so it has **zero enabled cleaning schedules and no next cleaning time**. Its two enabled records are internal do-not-disturb guards, not cleaning commands. Vendor OTA activity is not yet established by this investigation; services remain running while the known read-only update-state path is checked.

The schedule file was read over SSH on **October 21, 2026, at 04:48:21 UTC**. It is plain ASCII in AppProxy's native cron-like format, not encrypted JSON. Both records begin with `Y`, have schedule type `2` and recurring-time type `1`, and invoke only `dnd_start` or `dnd_stop`. Their minute field is `*`; complementary hour lists cover the first and second halves of each local day. These are minute-by-minute do-not-disturb guards, not an imminent scheduled clean. The separate server-timer file was empty at **04:48:06 UTC**.

This interpretation comes from the installed AppProxy's matching saved firmware, rather than a guessed decoder. The live and saved AppProxy MD5 values matched. In `binaries/4.3.5_1612/opt/rockrobo/cleaner/bin/AppProxy`, registration at **VA `0x625e8`** maps `get_timer` to **`0x67c34`**. That handler selects schedule types `1` and `2` only when the action class is `1`; the saved records have action class `2`. The native parser at **`0x87614`** reads the enable marker, record name, action class, time class and five cron fields in that order. The evaluator at **`0x86d74`** recognizes enabled recurring `dnd_start` guards separately. The constructor at **`0x86930`** selects `rockrobo/apptimer.cfg` and the vendor local-time file. All native inspection was static; original firmware code was not executed locally.

Calling the registered `get_timer` is unnecessary here and is not unconditionally read-only: **`0x67c34` can remove malformed entries through `0x86b18`** after assembling its reply. No timer RPC was sent. The saved-file observation does not independently inspect AppProxy's in-memory list, and external automation remains a separate command source.

The OTA registration also distinguishes two paths that should not be conflated. Both `miIO.get_ota_state` and `get_ota_state` use the thunk at **`0x6e384`**, which loads the updater object and branches to **`0x35558`**. That routine reads the current updater state and serializes a reply; its string table includes `idle`, `downloading`, `downloaded`, `wait_install`, `installing`, `installed` and `failed`. In contrast, the progress aliases use **`0x6e38c` → `0x33eac`**, whose nonzero-state path can invoke another updater routine after responding. No progress query has been sent. Absence of a `SysUpdate` process is not being treated as an OTA-idle result.
